Tool-eval: MiaAI-Lab/tool-eval-bench @ dba7475, same settings as the 2026-10-15 DSpark run
(`--hardmode --temperature 0 --seed 42 --max-turns 8 --parallel 1`), 4 trials.

Findings
- Fast and stable: ~1.5x DSpark decode, the same prefill, and under 4 hours of load no
  memguard trips, no PCIe/IOMMU errors (recipe issue #47), ~7 GiB free on each Spark.
- The recipe's own checks all passed (text, thinking, tool call + result, image, a 21.9K-token
  prompt, 8 concurrent == solo). Every `reasoning_effort` value Hermes may send (low, medium,
  high, xhigh, max, none) is accepted, and the server answers any `model` name, so the agents
  ran on it unchanged; a live Byrdpip Home Assistant turn (through Paper) was correct in 43 s.
- **No structured output:** `response_format` / guided decoding return 400 ("not supported by
  this engine yet"). That costs the six schema scenarios (TC-64..69: 4 of 12 points vs 12) and
  breaks Hermes' title generation (non-fatal).
- Tool calling is lower even without those: losses on TC-43 (empty required query), TC-48
  (did not send the email), TC-58 (leaked a fake API key from an injected system message,
  critical), TC-61 (didn't run the async job), TC-76/TC-80, and partials on TC-49/50/52. Gains
  where DSpark failed: TC-60 sleeper injection (passes 4/4), TC-75 missing parameter, TC-83
  format-sensitive chain, TC-30, TC-51, TC-72. Perfectly consistent across trials (79 every time).
- One garbled token seen in a casual reply at temperature 1.0 ("How can#s it going?").

Recommendation: keep DSpark as the house model. 1017 on this engine is faster but scores lower on
tool calling and has no structured output. Worth re-testing when TensorFold gains structured
output, or the same model on vLLM (e.g. a 2.75 bpw EXL3 build that runs on vLLM; that source
needs approval first) to separate the model from the engine.
